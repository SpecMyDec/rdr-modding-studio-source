## 1. How the game reads an action file (code facts, `03_Tools/research/probe_action_loader.py` PASS)

- **Loader** `0x002D81C0`: `opcode - 1001`, `sltiu 571`, jump table `0x00524490`. **296** of the 571
  slots have their own case; the other 275 fall to the default and are ignored. So the opcode space is
  1001..1571 and only 296 numbers do anything.
- Each case reads its arguments from the file through the stream object (vtable `+0x18` = int,
  `+0x0C` = quoted string, `+0x1C` = float) and stores them into the action's **property bag** with a
  numeric **kind**: setters `0x2DE180` (int), `0x2DE320` (float), `0x2DE4C0` (string/pointer), `0x2DDFE0`
  (byte). Some cases only OR a flag bit into the action record (`+0x8`, `+0xC`, `+0x10`).
  Bag = sorted array of `{s16 kind, u16, u32 value}`, binary-searched by `0x2DECE8`; `0x2DED80` returns
  the default from the table at `*0x0079F9D4` when a kind is absent.
- **Executor** `0x002E4E40` (the routine the 1560 HUD switch lives in) asks the bag for one kind after
  another and acts on each one present. Kind 1 is the action's "type" (62 opcodes just set kind 1 to a
  number, e.g. 1326 sets type 35).
- Opcodes that look like they take no argument (146 of them) are mostly flag setters or call a sub-parser
  (`0x2E9900` = an actor/target spec, e.g. 1018/1019 read `1, 11` or `1, 4, "Rachel"`; `0x2DC408` = a
  named action/state, used by 1004/1005/1006/1007). Those sub-grammars are NOT decoded here.
- Full per-opcode table (296 rows: case address, what it reads, which kind/flag it writes):
  `07_Research/op_loader_table.md` (+ `.json`), regenerated by the probe with `--md/--json`.

File layout seen while editing (enough to insert opcodes): an action is `u32 count` followed by `count`
opcodes, each `u32 opcode` + its arguments, no padding, strings quoted and NUL-terminated
(`"HowToZoom"\0`). Inserting an opcode = bump that count and splice the bytes in; nothing else in the file
has to change (proven: discs B, C, E, W below all grew the file and still ran).

## What the Studio could script today
An "event" = an action the level already runs, plus inserted opcodes. Proven building blocks: **teleport
(1032 + 1326)**, **HUD text box (1555)**, **door/zone stage (1544, state)**, HUD show/hide/lock (1560).
Not yet: the TRIGGER side ("enter area -> ..."): that lives in the `.stateb` condition records (1004 go to
state; area tests), which have their own sub-grammar (`0x2DC408`, `0x2E9900`) not decoded tonight. The
safe route for a first Studio feature is to append opcodes to an action that already runs (as done here),
not to author new state machines.

## 6. Trigger side: "when COND -> run action" (11/14, the reviewer Opus, opcode lane)

Grammar decoded from the executable (`03_Tools/research/probe_stateb_cond.py`, PASS) and encoded by
`07_Research/op_cond.py` + `07_Research/op_event.py` (`in_subroom`, `after_seconds`, `either`, `all_of`,
`trigger_entry`, `add_trigger`; `trigger_entry` reproduces the bytes of the proven discs exactly).
A trigger = a `1005 "ActionName" COND mode` entry appended to the END of a state in a `.stateb`
(bump that state's command count). `mode` (the u32 after COND) is 1 in every proof; its meaning is UNKNOWN
(stock files use 1..6).
